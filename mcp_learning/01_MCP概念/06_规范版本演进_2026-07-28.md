# 06 · 规范版本演进：从握手时代到无状态时代

> 这一篇解决一个很现实的困惑：
> **你在网上看到的 MCP 教程，一半是 Legacy 写法，一半是 Modern 写法，两者不能互相连。**
> 读完这篇，你能看着一个 Server 判断它属于哪个时代、该用什么姿势连它。

> 素材说明：`2026-07-28` 的 changelog 是**相对 `2025-11-25`** 的，不是相对 `2025-06-18`。
> 所以要看懂最新版，必须经过**两个跳板**（`2025-06-18` → `2025-11-25` → `2026-07-28`）。

---

## 一、版本链

| 修订 | 状态 | 一句话要点 |
| --- | --- | --- |
| `2024-11-05` | 已发布（传输已废弃） | 最早版本，用 **HTTP+SSE** 传输（两个端点：SSE 端点 + POST 端点） |
| `2025-03-26` | 已发布 | 引入 **Streamable HTTP** 取代 HTTP+SSE；单一 MCP endpoint；支持 `Last-Event-ID` 续传 |
| `2025-06-18` | 已发布 | **本系列的基线**；移除 JSON-RPC batching；生命周期 `SHOULD`→`MUST`；要求 `MCP-Protocol-Version` 头 |
| `2025-11-25` | 已发布 | 引入实验性 **tasks**、**URL 模式 elicitation**、**Sampling 支持 tool calling**、**Client ID Metadata Documents**、增量 scope 同意 |
| **`2026-07-28`** | **latest** | **重大破坏性变更：移除会话与 `initialize` 握手，转为无状态**；引入 MRTR、`server/discover`、`subscriptions/listen` |

**"latest" 的含义**：`https://modelcontextprotocol.io/specification/latest` 现在解析到 `/specification/2026-07-28`，
页面标题写明 `Version 2026-07-28 (latest)`。

> 所以：`2025-06-18` 目前**落后两个修订**，而且它的核心模型
> ——「状态化连接 + `initialize` 握手」—— 在最新版里已经被**移除**了。
> 学 Legacy 不是浪费时间（现存 Server 大量是 Legacy），但你必须知道它不是终点。

---

## 二、三个时代名词：Modern / Legacy / Dual-era

这三个词是规范 `basic/versioning` 页的**正式术语**（逐字）：

> - **Modern**：把版本、身份、能力作为逐请求元数据传递的协议版本（`2026-07-28` 及以后）。
> - **Legacy**：用 `initialize` 握手建立会话的协议版本（`2025-11-25` 及以前）—— **`2025-06-18` 属于 Legacy**。
> - **Dual-era**：同时支持两者的实现。

> There is no negotiation handshake. Every request carries its protocol version,
> and the server accepts or rejects each request independently.

### 兼容矩阵

| 组合 | 结果 | 为什么 |
| --- | --- | --- |
| Modern ↔ Modern | ✅ 可用 | 双方都按逐请求元数据说话 |
| Modern client ↔ Legacy server | ❌ **失败** | Modern client 不发 `initialize`，Legacy server 等不到握手 |
| Legacy client ↔ Modern server | ❌ **失败** | Modern server 没有 `initialize` 端点，Legacy client 的第一步就落空 |
| Dual-era ↔ 任一 | ✅ 可用 | 自己探测对方属于哪个时代 |

**关键结论：没有「向前回退」机制。**
双方不支持对方版本时，Server **MUST** 返回 `UnsupportedProtocolVersionError`（`-32022`）并列出自己支持的版本，
再由 client **SHOULD** 从中挑一个互相支持的版本**重试**。
如果 client 根本不支持任何列出的版本，那就只能失败。

> ⚠️ 这解释了一个非常常见的现象：**新版 SDK 连老 Server 报错、老客户端连新 Server 也报错**，
> 而且两边看起来都"没写错代码"。这不是 bug，是时代不匹配。
> 解决办法只有一个：把其中一端升级成 **Dual-era** —— 这正是 Python SDK v2 默认 `mode="auto"` 在做的事（见第七节）。

## 三、先看过渡版：`2025-11-25` 带来了什么

不看这一版，`2026-07-28` 的不少变更会显得没头没尾（比如"为什么 elicitation 有 URL 模式"）。

**Major changes（逐字要点）**：

| # | 变更 | 与后来的关系 |
| --- | --- | --- |
| 1 | 授权服务器发现支持 **OpenID Connect Discovery 1.0** | 授权发现链多一条 |
| 2 | 允许为 tools / resources / resource templates / prompts 暴露 `icons` 元数据 | 纯增量 |
| 3 | 通过 `WWW-Authenticate` 支持**增量 scope 同意** | 与 Scope 最小化配套 |
| 4 | 提供**工具命名指引** | 纯增量 |
| 5 | `ElicitResult` 与 `EnumSchema` 改用更标准的方案（带标题/无标题、单选/多选 enum） | 为 MRTR 铺路 |
| 6 | 新增 **URL 模式 elicitation** | 配套错误码 `-32042` |
| 7 | **Sampling 支持 tool calling**（`tools`、`toolChoice` 参数） | Sampling 已废弃，此能力随之退场 |
| 8 | 新增 **OAuth Client ID Metadata Documents** 作为推荐注册机制 | `2026-07-28` 用它取代 DCR |
| 9 | 新增实验性 **tasks**（轮询 + 延迟取结果） | `2026-07-28` 移出核心，成为官方扩展 |

**Minor 中值得记住的**：

- stdio 的 `stderr` 可用于**所有类型**日志（不只是错误）；无效 `Origin` **MUST** 返回 **403 Forbidden**；`WWW-Authenticate` 改为可选并回退到 `.well-known`。
- **输入校验错误应作为 Tool Execution Errors 返回**（而不是 Protocol Errors）—— 这是让模型自我纠正的唯一通道。
- 支持**轮询** SSE（server 可随时断开）；确立 **JSON Schema 2020-12** 为默认方言。

## 四、`2026-07-28` 的破坏性变更，逐条说清

以下 9 条是 Major / breaking 级别。**每一条都附"为什么"和"你该怎么办"**，不只是罗列。

### 1. 移除协议级会话与 `Mcp-Session-Id`

- **改了什么**：Streamable HTTP 上不再有协议级会话，`Mcp-Session-Id` 头**整个移除**。
  列表类端点（`tools/list`、`resources/list`、`prompts/list`）不再随连接变化。
- **为什么**：会话是水平扩展的敌人。有会话就必须做粘性路由、必须共享会话存储、必须处理会话过期，
  而 MCP 的大多数请求其实是**天然无状态**的（列工具、读资源）。
- **你该怎么办**：如果确实需要跨调用状态，**不要**往协议层塞，
  改用**显式、由 server 铸造的 handle 作为普通工具参数**传（这是规范给出的迁移方式，见 SEP-2567）。

### 2. MCP 变为无状态：移除 `initialize` / `notifications/initialized` 握手

- **改了什么**：握手整体删除。每个请求在 `_meta` 中携带协议版本与客户端能力：
  `io.modelcontextprotocol/protocolVersion`、`io.modelcontextprotocol/clientCapabilities`。
  此外 clients **SHOULD** 每个请求都标识自己（`io.modelcontextprotocol/clientInfo`），
  servers **SHOULD** 在每个结果的 `_meta` 中标识自己（`io.modelcontextprotocol/serverInfo`）。
  版本不匹配返回 `UnsupportedProtocolVersionError`（SEP-2575）。
- **为什么**：把协商摊到每个请求上，Server 就能被**无状态地横向扩展**，
  也不再有"连接建立时协商的能力，运行中被改掉"这类状态一致性问题。
- **你该怎么办**：删掉 `initialize` 相关代码；把原来"连接时确认一次"的东西改成"每个请求都带上"。
  用 SDK 的话，这部分由 SDK 自动注入，你基本无感。

### 3. 新增 `server/discover`

- **改了什么**：servers **MUST** 实现这个 RPC，用来宣告**支持的协议版本、能力与身份**。
  clients **MAY** 在其它请求前调用它做**前置版本选择**，在 STDIO 上则可作为**向后兼容探针**。
- **为什么**：没有握手了，客户端就必须有个"先问一句你是谁、支持什么"的口子。
  这就是 Modern 时代的 `initialize` 替代品 —— 但它是**普通请求**，不建立任何状态。
- **你该怎么办**：写 Modern server 必须实现它。返回体形如：

```json
{ "jsonrpc": "2.0", "id": "discover-1",
  "result": {
    "resultType": "complete",
    "supportedVersions": ["2026-07-28"],
    "capabilities": { "tools": {}, "resources": {} },
    "_meta": { "io.modelcontextprotocol/serverInfo": { "name": "ExampleServer", "version": "1.0.0" } },
    "instructions": "This server provides weather and resource utilities.",
    "ttlMs": 3600000, "cacheScope": "public"
  } }
```

  > 注意 `ttlMs` 与 `cacheScope`：`2026-07-28` 起 list/read 类结果新增这对**必填**缓存字段（`CacheableResult`），
  > `server/discover` 的结果也是可缓存的。这让 Client/网关可以安全地缓存发现结果。

### 4. `subscriptions/listen` 取代 GET SSE 与 `resources/subscribe`

- **改了什么**：HTTP **GET 端点被移除**，`resources/subscribe` / `resources/unsubscribe` 被取代。
  改为 **`subscriptions/listen`**：一条**长驻的 POST 响应流**。
  客户端按类型 opt-in：`toolsListChanged`、`promptsListChanged`、`resourcesListChanged`、`resourceSubscriptions`；
  server 确认订阅，并用 `io.modelcontextprotocol/subscriptionId` 标记后续通知。
- **为什么**：独立的 GET 事件流是"会话式"设计的产物（需要单独维护一条长连接、需要分配 event ID、需要续传）。
  换成"一个请求开一条监听流"后，订阅也变成了自包含的请求，和整体无状态方向一致。
- **你该怎么办**：把 `resources/subscribe` 改成 `subscriptions/listen` 并在一个请求里声明你关心哪几类变更。
  注意：**请求级通知**（`notifications/progress`、`notifications/message`）**不走**这条流，
  仍然走各自请求的响应流。

### 5. 移除 `ping`、`logging/setLevel`、`notifications/roots/list_changed`

- **改了什么**：
  - `ping` 保活机制**移除**。
  - `logging/setLevel` **移除**，日志级别改为**逐请求**的 `_meta` 键 `io.modelcontextprotocol/logLevel`；
    **未携带该字段的请求，servers MUST NOT 发出 `notifications/message`**。
  - `notifications/roots/list_changed` **移除**（Roots 整体废弃，见第六节）。
- **为什么**：`ping`、`setLevel` 都是**会话级**的控制手段 —— "给这条连接设个级别"。
  没有会话了，配置就必须跟着请求走。
- **你该怎么办**：删掉保活逻辑（改用你所在 HTTP 栈/传输层自己的健康检查）；
  需要日志时在**每个请求**上带 `logLevel`，否则一条日志都收不到（这是最容易踩的坑）。

### 6. tasks 移出核心协议

- **改了什么**：tasks 成为官方扩展 `io.modelcontextprotocol/tasks`；
  以 `tasks/get` 轮询 + `tasks/update` 取代阻塞式的 `tasks/result`，并**移除 `tasks/list`**。
- **为什么**：长任务编排属于"某些场景才需要"的能力，不该让所有实现都背上核心协议的复杂度。
- **你该怎么办**：如果之前用了 tasks，注意 `tasks/result` → `tasks/get` + `tasks/update` 的改法，并显式声明该扩展。

### 7. 引入 MRTR，取代「Server 主动发起请求」

- **改了什么**：**Multi Round-Trip Requests**。Server 不再主动发
  `roots/list` / `sampling/createMessage` / `elicitation/create`，
  而是返回 `InputRequiredResult`（`resultType: "input_required"`），
  其 `inputRequests` 字段携带所需输入；client 在**重试原请求**时用 `inputResponses` 提供。
  **旧的 server-initiated request 模式不再支持 —— 这是彻底的破坏性变更。**
- **为什么**：Server 主动发请求要求底层有双向通道 —— stdio 可以，普通 HTTP 不行。
  改成一问一答的"重试"模式后，**任何单向传输都能承载 Elicitation**，
  服务端实现也重新变成"收到请求 → 返回响应"的简单函数。
- **你该怎么办**：把"我要向用户要个值"从"发一个请求"改成"返回 `input_required` + `inputRequests`"。
  客户端侧则要支持**重试原请求**并带上 `inputResponses`（SDK 里由 `input_required_max_rounds` 之类机制兜住）。

### 8. 所有结果新增必填 `resultType`

- **改了什么**：普通结果为 `"complete"`，MRTR 中间结果为 `"input_required"`。
  对**省略该字段的旧版 server**，clients **MUST** 视为 `"complete"`。
- **为什么**：Client 必须能在**读到 `result` 的第一时间**判断"这是一个最终答案，还是一个需要我补输入的中途站"。
- **你该怎么办**：Server 侧所有结果都写上 `resultType`；Client 侧对缺字段的旧 Server 做默认为 `complete` 的兼容。

### 9. 移除 SSE 流续传与消息重投

- **改了什么**：`Last-Event-ID` 头与 SSE event ID **一并移除**。
- **为什么**：续传依赖"事件 ID 在会话内全局唯一"这个会话级前提，和"移除会话"直接冲突。
- **你该怎么办**：响应流中断即**丢失该在途请求**；clients **MUST** 以**新的 request ID** 重新发起。
  注意是**新的** request ID（旧 ID 不可重用，见 `02_架构与协议基础.md` 的 id 规则）。

### 顺带记住的 Minor 变更

- Capabilities 新增 **`extensions`** 字段（声明扩展支持的正式位置）；文档化 **OpenTelemetry trace context** 约定（`traceparent`、`tracestate`、`baggage`）。
- `tools/list` **SHOULD** 返回**确定性顺序**（为了可缓存）；HTTP POST **必须**带 `Mcp-Method`、`Mcp-Name` 头（便于网关路由），并可用 `x-mcp-header` 把工具参数镜像成 `Mcp-Param-{Name}` 头。
- 新增必填 `ttlMs` / `cacheScope`（见第 3 条）；**resource not found：`-32002` → `-32602`**（见下一节）。
- 放宽 Schema 能力：`inputSchema`/`outputSchema` 允许任意 JSON Schema 2020-12 关键字、`structuredContent` 允许任意 JSON 值，新增 `$ref` 解析要求与组合关键字资源上限。
- 授权侧：AS **SHOULD** 在授权响应中包含 `iss` 并 **MUST** 校验（RFC 9207）；client 凭据 **MUST** 按 issuer 键控、**MUST NOT** 跨 AS 复用。
- 移除 `notifications/elicitation/complete` 与 `elicitationId`（因为 elicitation 改走 MRTR）。

## 五、错误码重编号

`2026-07-28` 建立了明确的**错误码分配策略**（逐字）：

> JSON-RPC 2.0 reserves the range `-32000` to `-32099` for implementation-defined server errors.
> MCP partitions this range as follows:
> - **`-32000` to `-32019` — legacy.** … New codes **MUST NOT** be allocated in this sub-range …
>   Apart from `-32002` (see below), receivers **MUST NOT** assume any specific meaning for these codes.
> - **`-32020` to `-32099` — reserved for the MCP specification.** …
>   Implementations **MUST NOT** emit any code from this sub-range that is not defined by this specification.

现行定义的三个码：

| 码 | 名称 | 场景 |
| --- | --- | --- |
| `-32020` | `HeaderMismatch` | HTTP 头与请求不一致（规范只给出名称，未展开具体场景） |
| `-32021` | `MissingRequiredClientCapability` | 客户端缺少该请求必需的能力（规范只给出名称） |
| `-32022` | `UnsupportedProtocolVersion` | 版本不支持；**必须**在 `data.supported` 里列出支持的版本 |

**重编号对照（changelog 第 12 条，属 `2026-07-28` 草案内部的重编号）**：

| 名称 | 旧编号 | 新编号 |
| --- | --- | --- |
| `HeaderMismatch` | `-32001` | **`-32020`** |
| `MissingRequiredClientCapability` | `-32003` | **`-32021`** |
| `UnsupportedProtocolVersion` | `-32004` | **`-32022`** |

- **`-32002` 的命运**：resource not found 的错误码**从 `-32002` 改为 `-32602`（Invalid Params）**。
  实现本版 **MUST NOT** 再发出 `-32002`，但 clients **SHOULD** 仍**接受**来自旧版 server 的 `-32002`。
- `-32042`（URL elicitation required，2025-11-25 引入）**不可再发出**。
- 「纯本地」错误（例如 SDK 内部的请求超时）**目前未被规范分配任何码**；新增自定义错误码
  **SHOULD** 分配在 JSON-RPC 保留区间之外（即 `-32768` 到 `-32000` 之外）。

```json
{ "jsonrpc": "2.0", "id": 1,
  "error": { "code": -32022, "message": "Unsupported protocol version",
             "data": { "supported": ["2026-07-28", "2025-11-25"], "requested": "1900-01-01" } } }
```

> 对照阅读：`2025-06-18` 的 `schema.ts` **只导出 5 个标准码**（`-32700`/`-32600`/`-32601`/`-32602`/`-32603`），
> `-32000`~`-32099` **一个都没有**；`-32002` 只存在于文档正文。
> 所以「`-32001` 是 RequestTimeout」之类的说法从来不是规范内容（详见 `参考_规范逐字摘要.md` §13）。

## 六、废弃注册表（Deprecated registry）

| 特性 | 废弃于 | 迁移路径 | 最早移除 |
| --- | --- | --- | --- |
| **Roots** | `2026-07-28` | 通过**工具参数、资源 URI 或 server 配置**传递目录/文件 | 2027-07-28 当天或之后发布的第一个修订 |
| **Sampling** | `2026-07-28` | **直接集成 LLM provider API** | 同上 |
| **Logging** | `2026-07-28` | stdio 用 `stderr`；可观测性用 **OpenTelemetry** | 同上 |
| **Dynamic Client Registration（DCR）** | `2026-07-28` | **Client ID Metadata Documents** | 同上 |
| `includeContext: "thisServer"` / `"allServers"` | `2025-11-25` | 省略该字段或使用 `"none"` | 随 Sampling 一同移除 |
| HTTP+SSE transport（`2024-11-05`） | `2025-03-26` | Streamable HTTP | SEP-2596 Final 后三个月 |

**三条策略（逐字要点）**：

> A Deprecated feature remains part of the specification but is scheduled for removal:
> new implementations **SHOULD NOT** adopt it.

- 最短废弃窗口为 **12 个月**。
- 目前 **Removed 列表为空** —— 也就是说**没有任何东西被真正删掉**，废弃特性仍然可用，
  只是不该再用于新实现。

> **怎么读这张表**：`2026-07-28` 一次性把 **Roots / Sampling / Logging / DCR** 四个特性推进废弃通道，
> 这是 MCP 从"宿主什么都管"转向"Server 自己搞定"的信号：
> 要 LLM 就自己接 provider API，要日志就写 stderr/OTel，要目录边界就用工具参数传，
> 要客户端注册就用 Client ID Metadata Documents。

## 七、对你的实际影响（Python SDK v2）

**好消息**：SDK 已经把时代适配做掉了。你不需要自己写探测逻辑。

### `Client` 的 `mode` 参数

| 取值 | 行为 | 什么时候用 |
| --- | --- | --- |
| **`"auto"`（默认）** | **先探 `server/discover`，失败则回退 `initialize` 握手** | 默认就用它 —— 两种时代的 server 都能连 |
| `"legacy"` | 强制走 `initialize` 握手 | 需要 server→client 推送（Sampling / push elicitation / `message_handler`） |
| `"2026-07-28"` | 直接采用 Modern，零协商 | 明确知道对端是 Modern；注意此时 `server_info` 为 `None` |

配合 `prior_discover=client.session.discover_result` 可以**零往返**拿回服务器身份。

```python
from mcp import Client

async with Client(server) as client:          # mode 默认 "auto"
    tools = await client.list_tools()
    print(client.protocol_version, client.server_info)
```

**所以"两种时代的 server 都能连"不是巧合，是 `mode="auto"` 的探测顺序决定的**：
先按 Modern 问一句 `server/discover`，对方不认（旧 Server 会返回方法不存在一类的错误），
就退回 Legacy 的 `initialize` 握手。

### 其他要留意的 SDK v2 行为

- 客户端会**按协商出的版本校验入站报文**；不合规的服务器会抛 `pydantic.ValidationError`
  —— 这其实是好事，能把"看起来能跑但不符合规范"的 Server 早点暴露出来。
- `cursor` 参数**从 `ClientSession` 的列表方法上移除**（分页改由 `Client` 层处理，`list_*` 方法仍接受 `cursor=` 并返回 `next_cursor`）。
- 超时改为 **float 秒**；**超时错误码 `-32001`（`REQUEST_TIMEOUT`）取代了原来的 HTTP `408`**。
  ⚠️ 注意：`-32001` 属于 **SDK 实现层**，不是规范定义的码（规范里这个子区间是 legacy）。
- 现代连接上：`client.subscribe_resource(uri)` / `unsubscribe_resource(uri)` 返回 `-32601`，
  替代方案是 `async with client.listen(...)`；`client.send_ping()` 已废弃（现代服务端答 Method not found）。

### 一张"老写法 → 新写法"对照表

| `2025-06-18` 做法 | `2026-07-28` 应改为 |
| --- | --- |
| `initialize` + `notifications/initialized` 握手 | 删除握手；每个请求在 `_meta` 带 `protocolVersion` + `clientCapabilities` |
| 依赖 `Mcp-Session-Id` 维持状态 | 无会话；跨调用状态用 server 铸造的显式 handle 作为工具参数 |
| `resources/subscribe` + HTTP GET SSE 流 | `subscriptions/listen` 长驻 POST 响应流 |
| server 主动发 `roots/list` / `sampling/createMessage` / `elicitation/create` | MRTR：返回 `InputRequiredResult.inputRequests`，client 重试时带 `inputResponses` |
| `logging/setLevel` + `notifications/message` | 逐请求 `_meta` 的 `io.modelcontextprotocol/logLevel` |
| `ping` 保活 | 已移除 |
| `roots/list` 获取目录边界 | Roots 已废弃，改用工具参数 / 资源 URI / server 配置 |
| `sampling/createMessage` | Sampling 已废弃，直接集成 LLM provider API |
| SSE `Last-Event-ID` 续传 | 已移除；中断后以**新的 request ID** 重发 |
| `-32002` resource not found | `-32602`（但 client 仍应接受旧 server 的 `-32002`） |

## 八、自测

**1. `2025-06-18` 属于 Modern 还是 Legacy？为什么这个分类会影响你的选型？**

<details><summary>答案</summary>

属于 **Legacy**。规范的 `basic/versioning` 定义：Legacy 是"用 `initialize` 握手建立会话的协议版本（`2025-11-25` 及以前）"，
所以 `2025-06-18` 和 `2025-11-25` 都是 Legacy；Modern 是 `2026-07-28` 及以后。
影响在于兼容矩阵：**Modern client ↔ Legacy server 失败，Legacy client ↔ Modern server 失败**，
而且**没有向前回退机制**。所以选型时你必须在"支持面广"（做 Dual-era，如 Python SDK v2 的 `mode="auto"`）
和"只用新特性"（纯 Modern，但要接受连不上老 Server）之间做选择。
`2025-06-18` 上的手写 Server 现在落后两个修订，其核心的"状态化连接 + 握手"模型已被移除。

</details>

**2. `2026-07-28` 移除了 `initialize` 握手，那"客户端能力"和"协议版本"改从哪里传？**

<details><summary>答案</summary>

改成**逐请求**在 `_meta` 里传：
`io.modelcontextprotocol/protocolVersion` 与 `io.modelcontextprotocol/clientCapabilities`。
另外 clients **SHOULD** 每个请求都标识自己（`io.modelcontextprotocol/clientInfo`），
servers **SHOULD** 在每个结果的 `_meta` 中标识自己（`io.modelcontextprotocol/serverInfo`）。
版本不匹配时返回 `UnsupportedProtocolVersionError`（`-32022`），并在 `data.supported` 里列出支持的版本。
同时新增 `server/discover`：servers **MUST** 实现它来宣告支持的版本、能力与身份，
clients **MAY** 用它做前置版本选择，或在 STDIO 上作为向后兼容探针。

</details>

**3. MRTR 是什么？它为什么比"Server 主动发请求"更好？**

<details><summary>答案</summary>

MRTR = **Multi Round-Trip Requests**。Server 不再主动发
`roots/list` / `sampling/createMessage` / `elicitation/create`，而是返回
`InputRequiredResult`（`resultType: "input_required"`），其 `inputRequests` 字段说明需要什么输入；
client 在**重试原请求**时用 `inputResponses` 提供答案。
更好的原因是：server-initiated request 要求底层有**双向通道**（stdio 可以，普通 HTTP 不行），
而"返回 `input_required` → 客户端重试"把交互压回了标准的"一问一答"形状，
**任何单向传输都能承载 Elicitation**，服务端也重新变成简单的请求-响应函数。
注意这是**破坏性变更**：旧的 server-initiated request 模式**不再支持**。

</details>

**4. 你在写一个 Modern server，需要给 `tools/list` 发日志。需要做什么？**

<details><summary>答案</summary>

需要让**每个请求**在 `_meta` 里带上 `io.modelcontextprotocol/logLevel`
（因为 `logging/setLevel` 已被移除，日志级别改为逐请求传入）。
关键约束：**未携带该字段的请求，servers MUST NOT 发出 `notifications/message`** ——
所以如果你之前用会话级 `setLevel` 控制日志，现在会在客户端看到"一条日志都收不到"。
另外 `2026-07-28` 还把 Logging 整体推进了废弃通道（迁移路径：stdio 用 `stderr`，可观测性用 OpenTelemetry），
新实现应当考虑直接跳过日志通知。

</details>

**5. `2026-07-28` 里 `-32002`、`-32020`、`-32022` 分别是什么？**

<details><summary>答案</summary>

- **`-32002`**：Legacy 的 resource not found，**已被 `-32602`（Invalid Params）取代**。本版实现 **MUST NOT** 再发出它，但 clients **SHOULD** 仍接受旧 server 发来的 `-32002`。
- **`-32020`**：`HeaderMismatch`（HTTP 头与请求不一致），由 `-32001` 重编号而来；**`-32022`**：`UnsupportedProtocolVersion`（必须在 `data.supported` 列出支持版本），由 `-32004` 重编号而来。
- **`-32021`** = `MissingRequiredClientCapability`（由 `-32003` 重编号）。分配策略：`-32000`~`-32019` 为 **legacy**（新码 **MUST NOT** 分配在此，接收方除 `-32002` 外 **MUST NOT** 假设含义）；`-32020`~`-32099` 保留给规范；自定义码 **SHOULD** 分配在 JSON-RPC 保留区间之外。

</details>
