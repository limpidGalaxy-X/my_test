# 02 · 架构与协议基础

> 本篇讲清楚：谁跟谁说话、说什么格式、怎么开始、怎么结束。
> 内容以 **2025-06-18 / 2025-11-25（"Legacy" 握手时代）** 为主线，
> 因为这是绝大多数 Host 与教程仍在用的模型；`06_规范版本演进_2026-07-28.md` 讲最新的无状态模型。

---

## 一、三个角色，职责严格分离

### Host（宿主应用）

用户直接面对的 AI 应用。它负责：

- 创建和管理**多个** Client 实例
- 控制每个连接**允不允许**建立、什么时候断开
- 执行安全策略、**征得用户同意**
- 把各 Server 提供的上下文**聚合**起来交给 LLM
- 处理模型返回的 function calling 意图 → 转成 MCP 调用

### Client（连接器）

Host 内部**为每一个 Server 单独开一条**连接。它负责：

- 与**一个** Server 建立**有状态会话**（1 Client : 1 Server）
- 协议版本与能力协商
- 双向消息路由、订阅与通知
- 维持不同 Server 之间的**安全边界**

> ⚠️ 最容易搞错的一点：**Client 不是"应用"，是"连接"。**
> Claude Desktop 连了 GitHub、文件系统、Postgres 三个 Server，那就是 3 个 Client。

### Server（能力提供方）

- 通过原语暴露 Resources / Prompts / Tools
- 职责单一、可组合
- **不能**读取完整对话，**不能**"看进"别的 Server
- 可以是本地子进程，也可以是远程服务

### 设计原则（规范原文）

| 原则 | 含义 |
| --- | --- |
| Servers should be **extremely easy to build** | 写一个 Server 应该只要几十行 |
| Servers should be **highly composable** | 多个小 Server 组合出复杂能力 |
| Servers **should not** read the whole conversation | 隐私边界：Server 只看到自己该看的 |
| Features can be added **progressively** | 能力是可选的，按需实现 |

### 拓扑图

```
┌─────────────────────── MCP Host（AI 应用）───────────────────────┐
│  安全策略 / 用户同意 / 授权 / 上下文聚合 / LLM 调用与 sampling 协调  │
│                                                                  │
│   ┌───────────┐   ┌───────────┐   ┌───────────┐   ┌───────────┐  │
│   │ Client #1 │   │ Client #2 │   │ Client #3 │   │ Client #4 │  │
│   └─────┬─────┘   └─────┬─────┘   └─────┬─────┘   └─────┬─────┘  │
└─────────┼───────────────┼───────────────┼───────────────┼────────┘
          │               │               │               │
      stdio           stdio        Streamable HTTP   Streamable HTTP
          │               │               │               │
   ┌──────▼─────┐  ┌──────▼─────┐  ┌──────▼─────┐  ┌──────▼─────┐
   │ Server: 文件 │  │ Server: Git │  │ Server: DB │  │Server: 搜索 │
   └────────────┘  └────────────┘  └────────────┘  └────────────┘

   Client → Server ：Resources / Prompts / Tools
   Server → Client ：Sampling / Roots / Elicitation（2026-07-28 起仅剩 Elicitation 的替代形态）
```

**Server 之间互相看不见。** 想让 A 把数据给 B，只能通过 Host 中转。

## 二、协议基础：JSON-RPC 2.0

MCP 的**所有**消息都是 JSON-RPC 2.0。只有三种形态：

### 1. Request（请求，需要回复）

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/call",
  "params": { "name": "get_weather", "arguments": { "location": "New York" } }
}
```

- `id` 不能是 `null`，同一会话内不能复用同一个 id（用来匹配响应）

### 2. Response（响应）

成功：

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "result": {
    "content": [{ "type": "text", "text": "Current weather in New York: 72°F, Partly cloudy" }],
    "isError": false
  }
}
```

失败：

```json
{
  "jsonrpc": "2.0",
  "id": 5,
  "error": { "code": -32002, "message": "Resource not found",
             "data": { "uri": "file:///nonexistent.txt" } }
}
```

- `result` 和 `error` **不能同时出现**
- 错误码必须是整数

### 3. Notification（通知，不需要回复）

```json
{ "jsonrpc": "2.0", "method": "notifications/tools/list_changed" }
```

- **不能**有 `id`；收到通知的一方**不能**回复

> 2025-06-18 起**不支持批量（batching）**，一次一条消息。

## 三、能力协商（Capability Negotiation）

不是所有实现都支持全部功能，所以握手时要互相"报菜名"。

### 客户端可以声明

| 能力 | 说明 |
| --- | --- |
| `roots` | 支持告知 Server 可操作的文件系统边界（`listChanged` 可选） |
| `sampling` | 支持 Server 反向请求 LLM 生成 |
| `elicitation` | 支持 Server 向用户追问信息 |
| `experimental` | 实验特性 |

### 服务端可以声明

| 能力 | 说明 |
| --- | --- |
| `tools` | 提供工具（`listChanged` 可选） |
| `resources` | 提供资源（`subscribe`、`listChanged` 可选） |
| `prompts` | 提供提示词模板（`listChanged` 可选） |
| `logging` | 支持协议级日志级别控制 |
| `completions` | 支持参数自动补全 |
| `experimental` | 实验特性 |

**规则**：双方**只能使用成功协商过的能力**。

## 四、生命周期（Legacy：握手 → 操作 → 关闭）

```
   Client                                          Server
     │                                                │
     │──── 1. initialize ────────────────────────────►│
     │     (protocolVersion, capabilities, clientInfo)│
     │                                                │
     │◄─── 2. InitializeResult ───────────────────────│
     │     (protocolVersion, capabilities,            │
     │      serverInfo, instructions?)                │
     │                                                │
     │──── 3. notifications/initialized ─────────────►│
     │                                                │
     │═══════════ 4. Operation（正常收发）══════════════│
     │  tools/list, tools/call, resources/read, ...   │
     │  notifications/progress, notifications/cancelled ...│
     │                                                │
     │──── 5. Shutdown（靠传输层，没有专门消息）─────────│
     │     stdio: 关闭子进程 stdin → SIGTERM → SIGKILL │
     │     HTTP : 关闭连接 / DELETE 会话               │
```

### 1. initialize 请求（真实报文）

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "initialize",
  "params": {
    "protocolVersion": "2025-06-18",
    "capabilities": {
      "roots": { "listChanged": true },
      "sampling": {},
      "elicitation": {}
    },
    "clientInfo": { "name": "ExampleClient", "title": "示例客户端", "version": "1.0.0" }
  }
}
```

### 2. 响应

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "protocolVersion": "2025-06-18",
    "capabilities": {
      "logging": {},
      "prompts": { "listChanged": true },
      "resources": { "subscribe": true, "listChanged": true },
      "tools": { "listChanged": true }
    },
    "serverInfo": { "name": "ExampleServer", "title": "示例服务器", "version": "1.0.0" },
    "instructions": "Optional instructions for the client"
  }
}
```

### 3. 就绪通知

```json
{ "jsonrpc": "2.0", "method": "notifications/initialized" }
```

### 关键字段

| 字段 | 含义 |
| --- | --- |
| `protocolVersion` | 版本号，形如 `"2025-06-18"`（日期式） |
| `capabilities` | 能力声明 |
| `clientInfo` / `serverInfo` | `{name(必填), title?, version?}` |
| `instructions` | 给模型看的服务器使用说明（Host 会塞进系统提示） |

### 版本协商规则

1. Client 发自己支持的版本（**应**发最新的）
2. Server 支持 → **必须**回同一版本；不支持 → **必须**回一个自己支持的版本
3. Client 不接受 → **应**断开

### 顺序约束

- Client **不应**在收到 initialize 响应前发非 `ping` 请求
- Server **不应**在收到 `initialized` 前发非 `ping`/日志请求

### Shutdown

协议里**没有** `shutdown` 方法，靠传输层：

- **stdio**：Client 关闭子进程 stdin → 等退出 → 超时 `SIGTERM` → 再超时 `SIGKILL`
- **HTTP**：关闭连接；Protocol 2025-06-18 可用 HTTP `DELETE` 结束会话

## 五、常用方法名一览

| 方向 | 方法 |
| --- | --- |
| 基础 | `initialize`、`ping`、`notifications/initialized`、`notifications/cancelled`、`notifications/progress` |
| 工具 | `tools/list`、`tools/call`、`notifications/tools/list_changed` |
| 资源 | `resources/list`、`resources/read`、`resources/templates/list`、`resources/subscribe`、`resources/unsubscribe`、`notifications/resources/list_changed`、`notifications/resources/updated` |
| 提示词 | `prompts/list`、`prompts/get`、`notifications/prompts/list_changed` |
| 补全 | `completion/complete` |
| 日志 | `logging/setLevel`、`notifications/message` |
| 客户端能力 | `roots/list`、`notifications/roots/list_changed`、`sampling/createMessage`、`elicitation/create` |

**命名规律**：`类别/动作`。反向（Server → Client）的请求用**单数名词**：`roots/list`、`sampling/createMessage`。

## 六、错误码

### 标准 JSON-RPC 2.0（MCP 全部沿用）

| 码 | 名称 | 典型场景 |
| --- | --- | --- |
| `-32700` | Parse error | JSON 解析失败 |
| `-32600` | Invalid Request | 不是合法请求对象 |
| `-32601` | Method not found | 不支持的方法（如 Server 不支持 roots） |
| `-32602` | Invalid params | **未知工具名**、参数不合法、无效 cursor、无效日志级别 |
| `-32603` | Internal error | 内部错误 |

### MCP 相关

| 码 | 名称 | 说明 |
| --- | --- | --- |
| `-32002` | Resource not found | **仅出现在 2025-06-18 规范正文**；schema 未定义该常量。2026-07-28 起被 `-32602` 取代 |
| `-32020` | HeaderMismatch | 2026-07-28 新增 |
| `-32021` | MissingRequiredClientCapability | 2026-07-28 新增 |
| `-32022` | UnsupportedProtocolVersion | 2026-07-28 新增 |

> ⚠️ 网上常见的 `-32000 Connection closed` / `-32001 Request timeout` **不是规范里的码**，
> 那是 TypeScript SDK 自己定义的实现细节（Python SDK 只保留了 `CONNECTION_CLOSED`）。

### 工具错误的两条通道（非常重要）

| 类型 | 用什么 | 例子 |
| --- | --- | --- |
| **协议错误**（Protocol Error） | JSON-RPC `error` 对象 | 未知工具名、参数格式非法、服务器崩溃 |
| **工具执行错误**（Tool Execution Error） | 正常 result 里的 `isError: true` | API 调用失败、业务规则不满足、输入数据无效 |

规范明确建议：**输入数据有问题时用 `isError: true`**，这样模型能看到错误信息并**自我纠正**；用 JSON-RPC error 的话模型往往看不到。

在 SDK 里就对应（下面这段是实测结果）：

```python
raise ToolError("文件不存在")   # -> is_error=True，文本原样："Error executing tool read_file: 文件不存在"
raise RuntimeError("内部错误")  # -> 也是 is_error=True，但文本被吞成："Error executing tool always_crashes"
                               #    真实堆栈只写进服务器 stderr 日志，模型看不到细节，无法自我纠正
raise MCPError(...)            # -> 变成 JSON-RPC error 对象（模型看不到）
```

**规律**：只有 `ToolError` 的消息会**原样**传给模型。
这解释了为什么规范强调「输入校验错误应作为 Tool Execution Errors 返回」—— 那是唯一能让模型自我纠正的通道。

> 补充：参数校验失败（pydantic 拦下的）也会自动变成 `is_error=True`，
> 消息形如 `1 validation error for search_docsArguments ...`。
